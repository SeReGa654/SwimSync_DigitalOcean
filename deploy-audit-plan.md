# SwimSync pre-deploy audit

## Висновок

Критичних блокерів для деплою не знайшов. Основні ризики зараз — не зламана логіка, а не до кінця послідовний користувацький шлях і кілька UX-місць, де система поводиться технічно правильно, але нечітко для користувача.

## Уже перевірено як ок

- [x] Публічне live-табло працює лише для ` /competitions/:id/live `.
- [x] Нормативи та WA base times читаються публічно.
- [x] Імпорт має завершальний крок підтвердження через `EventConstructor`.
- [x] Форма підтримки і help-центр послідовно вимагають авторизацію для створення тікета.

## Що варто допрацювати перед сервером

### 1. Зробити помилки доступу людяними
- **Де:** `frontend/src/app/competitions/[id]/page.tsx`
- **Що:** зараз неавторизований користувач бачить загальну помилку завантаження замість пояснення, що розділ захищений.
- **Навіщо:** користувач має одразу розуміти, куди йти далі.
- [x] Виправлено: сторінка показує пояснення та CTA на `/login`.

### 2. Додати явний “наступний крок” у картці змагання
- **Де:** `frontend/src/app/competitions/[id]/page.tsx`
- **Що:** на сторінці вже є статуси `draft / active / completed`, але бракує короткого сценарного підказувача:
  - draft → імпорт
  - active → секретар / live
  - completed → результати / експорти
- **Навіщо:** це прибирає плутанину у послідовності роботи.
- [x] Виправлено: додано статусний блок “Наступний крок”.

### 3. Прибрати мовчазний редірект з `/operator`
- **Де:** `frontend/src/app/operator/page.tsx`
- **Що:** редірект у `/admin` зараз нічим не пояснений.
- **Навіщо:** користувач не розуміє, чому потрапляє в інший розділ.
- [x] Виправлено: `/operator` показує пояснення і кнопки дії.

### 4. Уніфікувати вхідний шлях для ролей
- **Де:** `frontend/src/app/admin/page.tsx`, `frontend/src/app/secretary/page.tsx`, `frontend/src/app/competitions/page.tsx`
- **Що:** логін уже є, але він розкиданий по кількох рольових сторінках.
- **Навіщо:** це працює, але для першого входу краще мати один очевидний маршрут або хоча б спільну точку входу.
- **Статус:** не блокер, але варто для передбачуваності UX.
- [x] Виправлено: додано окрему `/login` як спільну точку входу та переведено основні CTA на неї.

### 5. Додати явні підказки для гостьових сторінок
- **Де:** `frontend/src/app/help/page.tsx`, `frontend/src/app/contacts/page.tsx`
- **Що:** форма підтримки вимагає авторизації; це вже вказано, але варто тримати це формулювання максимально помітним на старті форми.
- **Навіщо:** менше помилкових спроб від гостей.
- [x] Виправлено: CTA ведуть на `/login`, а повідомлення про авторизацію лишилось помітним.

### 6. Перевірити, що список змагань не дає “порожнього тупика”
- **Де:** `frontend/src/app/competitions/page.tsx`
- **Що:** якщо користувач не має доступних змагань, екран має чітко вести до створення/реєстрації, а не просто констатувати відсутність даних.
- **Навіщо:** щоб новий користувач не губився в першому кроці.
- [n/a] Наразі `/competitions` є редіректом на секретарський workflow, окремого public empty-state екрана там немає.

### 7. Закрити контрольні поверхні для admin-only
- **Де:** `backend/src/competitions/competitions.controller.ts`, `backend/src/results/results.controller.ts`, `backend/src/feature-flags/feature-flags.controller.ts`, `frontend/src/app/admin/page.tsx`, `frontend/src/components/operator/OperatorDashboard.tsx`, `frontend/src/app/secretary/page.tsx`, `frontend/src/app/competitions/[id]/tabs/SettingsTab.tsx`
- **Що:** керування змаганнями, протоколами, фіче-флагами та локальні admin tools більше не повинні бути доступні не-admin ролям; localhost-посилання мають не показуватись у production.
- **Навіщо:** це прибирає розсинхрон між UI та бекендом і не показує користувачу локальні адреси після деплою.
- [x] Виправлено: контрольні маршрути переведені на admin-only, а локальні тулзи приховані в production build.
